# 共创平台项目库 / 资产库 / 版本引用改造设计

日期：2026-07-17

## 1. 目标

本次改造围绕三个核心问题：

1. 工作台中的“参考资产”只能上传，不能直接从当前项目已有版本中选择。
2. 项目库和资产库信息层级不清，无法形成“项目 -> 版本 -> 定稿图 / Prompt 资产”的闭环。
3. 顶部导航、按钮和页面布局在桌面端与移动端都不够稳定，资产库也缺少明确的“添加资产”入口与发布路径。

目标是先在当前前端本地存储架构上完成一版可运行闭环：

- 工作台支持“上传外部资产”与“从当前项目版本中选一个”两种参考资产入口。
- 顶部导航明确分为“工作台 / 项目库 / 资产库”。
- 项目库采用卡片式项目列表，进入项目后查看版本列表，再进入版本详情查看 Prompt、结果说明、生成图和操作。
- 资产库只收录用户满意后定稿并发布的资产，包含定稿图与 Prompt 库，并提供显式添加入口。
- UI 同步做一轮结构和视觉优化，重点解决按钮层级、布局密度和移动端顶部导航错位问题。

## 2. 当前实现约束

当前仓库没有后端持久化能力接入，本次实现继续基于以下本地存储键：

- `cocreation:projects`
- `cocreation:version_snapshots`
- `cocreation:reference_asset`
- `cocreation:asset_library`

当前已有页面与组件职责如下：

- `frontend/src/App.tsx`
  - 顶部导航和工作台 / 项目库 / 资产库切换入口
- `frontend/src/components/CoCreationHistoryPage.tsx`
  - 项目库与资产库复用页
- `frontend/src/components/CoCreationAgentWorkspace.tsx`
  - 工作台、版本快照、参考资产、发布资产逻辑

因此本次改造不引入新路由，不新建全局状态管理，优先在现有组件内重组结构与数据模型。

## 3. 信息架构

### 3.1 导航层级

保留单页壳层，顶部主导航固定为：

- 工作台
- 项目库
- 资产库

工作台负责创作与引用。

项目库负责管理“项目”和其下“版本”。

资产库负责管理已发布资产，不展示未定稿草稿。

### 3.2 项目库层级

项目库采用三级浏览结构，但在单页内完成，不新增独立路由：

1. 项目列表
2. 版本列表
3. 版本详情

交互形态：

- 左侧或上方：项目卡片网格
- 选中项目后：展示该项目下的版本时间线 / 列表
- 选中版本后：右侧或下方展示版本详情

版本详情至少包含：

- 版本名
- 创建时间
- 状态
- 来源项目
- Prompt
- 优化后 Prompt
- 结果说明
- 预览图
- 诊断信息
- “设为参考资产”
- “发布到资产库”
- “删除版本”

### 3.3 资产库层级

资产库按内容类型拆成两个主分区：

- 项目定稿图
- Prompt 库

每个资产都保留来源链路：

- 来源项目名
- 来源版本
- 发布时间
- 是否定稿

添加资产按钮点击后弹出选择面板，提供三种入口：

1. 从项目版本发布
2. 上传外部资产
3. 新建 Prompt 资产

第一版里，“上传外部资产”和“新建 Prompt 资产”可以先做轻量表单，不要求接真实后端。

## 4. 数据模型调整

### 4.1 项目与版本关系

当前项目聚合逻辑依赖 `sourceObject || label`，会导致项目名与版本名混淆。需要在前端本地层面补齐稳定关系字段：

- `ProjectRecord.id`
- `ProjectRecord.name`
- `VersionSnapshot.projectId`
- `VersionSnapshot.projectName`
- `VersionSnapshot.versionNumber`
- `VersionSnapshot.isFinalized`

兼容策略：

- 读取旧数据时，如果缺少新字段，则通过现有 `sourceObject`、`label` 和时间戳推导。
- 保存新版本时，优先写入新字段。
- `groupProjects` 改为基于 `projectId` 聚合，`projectName` 只作为展示字段。

### 4.2 资产发布关系

资产项新增或统一以下字段：

- `id`
- `kind`
- `title`
- `description`
- `prompt`
- `imageUrl`
- `sourceProjectId`
- `sourceProjectName`
- `sourceVersionId`
- `sourceVersionLabel`
- `createdAt`
- `isFinalized`

发布逻辑要求：

- 只有满意并定稿的版本允许发布到资产库。
- 同一版本再次发布时，用“该版本重新发布覆盖旧资产”的策略，避免重复堆积。
- Prompt 资产与图片资产并行生成，但都挂在同一个版本上。

## 5. 工作台改造

### 5.1 参考资产入口

工作台“参考资产”区域调整为双入口：

- 上传
- 选项目版本

点击“选项目版本”后必须弹出版本选择弹窗，不再静默写入。

弹窗内容：

- 当前项目名称
- 当前项目全部版本列表
- 每个版本的缩略图、时间、状态、摘要
- 单选版本
- 确认后写入 `selectedReferenceAsset`

如果当前项目没有版本，弹窗内明确提示“当前项目暂无可引用版本”。

### 5.2 参考资产展示

工作台选中参考资产后，卡片中展示：

- 来源项目
- 版本名
- 预览图
- Prompt 摘要
- 清除按钮

这样用户知道当前生成是基于哪个历史版本继续演进。

## 6. 页面视觉与布局

### 6.1 顶部壳层

顶部固定条改成更稳的两段式结构：

- 左侧：产品名称 + 导航标签
- 右侧：用户信息 + 退出

移动端规则：

- 顶部允许换行，但不能压缩成竖排文字
- 导航标签转为横向滚动或两行稳态布局
- 主按钮高度统一，避免重叠

### 6.2 项目库

项目库采用“卡片列表 + 详情面板”的工作台式布局：

- 项目卡片展示封面图、项目名、行业、版本数、最近更新时间
- 选中卡片后高亮
- 版本列表采用较紧凑的时间线或堆叠卡片
- 版本详情区重点展示结果图和 Prompt，而不是堆字段

### 6.3 资产库

资产库不再只是两个简单列表，而是一个完整资源台：

- 顶部统计与添加入口
- 图像资产网格
- Prompt 资产列表 / 卡片
- 空态设计
- 来源信息与快速复用操作

按钮视觉统一为主次两级：

- 主按钮：深色实底
- 次按钮：浅底描边
- 危险操作：单独红色语义

## 7. 关键交互

### 7.1 版本发布到资产库

从版本详情点击“发布到资产库”：

1. 校验版本是否有可发布内容
2. 标记该版本为定稿或已发布
3. 生成图片资产和 Prompt 资产
4. 写入资产库
5. 给出成功反馈

### 7.2 资产库添加

点击“添加”后弹出添加面板：

1. 从项目版本发布
2. 上传外部图片或设计图
3. 手工录入 Prompt 资产

第一项与项目库数据联动。

第二项和第三项直接写本地存储。

### 7.3 项目版本继续引用

工作台在当前项目存在版本时：

1. 点击“选项目版本”
2. 打开弹窗
3. 选择某版本
4. 写入参考资产
5. 回到工作台显示已引用状态

## 8. 错误处理与兼容

需要处理以下边界：

- 本地存储为空
- 老数据缺少 `projectId`、`projectName`、`isFinalized`
- 当前项目无版本
- 版本无图片或无 Prompt
- 重复发布同一版本
- 移动端宽度过窄时顶部导航溢出

处理原则：

- 不因旧数据结构而崩溃
- 所有空态必须给出明确文案
- 选择弹窗和添加弹窗必须可关闭
- 所有 destructive 操作都要确认

## 9. 实施范围

本轮只做前端本地版本，范围包含：

- `frontend/src/App.tsx`
- `frontend/src/components/CoCreationHistoryPage.tsx`
- `frontend/src/components/CoCreationAgentWorkspace.tsx`
- 可能新增少量本地帮助函数或类型定义文件

本轮不做：

- 后端持久化
- 多人协作权限
- 资产标签 / 搜索 / 收藏
- 版本 diff / 恢复 / 分支
- 真实对象存储上传

这些内容在下一阶段再做。

## 10. 验收标准

完成后以以下结果为准：

1. 工作台“选项目版本”点击后必定出现可操作弹窗。
2. 选中项目版本后，工作台能看到已引用的版本信息。
3. 顶部能稳定切换“工作台 / 项目库 / 资产库”。
4. 项目库可以看到多个项目卡片，点开后能看到多个版本，再点开能看到 Prompt 和生成图详情。
5. 资产库能看到已发布的定稿图和 Prompt 资产。
6. 资产库顶部有“添加”按钮，且可新增资产。
7. 桌面端与移动端布局不重叠、不挤压、不出现关键按钮遮挡。

## 11. 实施建议

推荐按以下顺序落地：

1. 先修正数据模型与项目聚合逻辑
2. 再改工作台参考资产选择弹窗
3. 再重做项目库结构
4. 最后重做资产库与顶部导航视觉

这个顺序能先解决“数据不稳定导致 UI 失真”的根问题，再处理界面层。
